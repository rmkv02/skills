# AGENTS.md

Репозиторий agent skills. Инструкции для агента, работающего **над этим репозиторием**. Полные нормы — `SPEC.md`; здесь то, что нужно, чтобы не сломать репозиторий.

```
skills/<layer>/<name>/SKILL.md   единственный источник правды
registry.yaml                    состав, владельцы, границы, профили
evals/routing-matrix.json        матрица роутинга репозитория
scripts/install.sh               установка профилями
scripts/validate_skills.py       валидатор = определение корректности
```

Слои: `lang` (форма и идиоматика языка) · `practice` (процесс вне языка) · `platform` (инфраструктура).

## Инварианты

1. Правь только `skills/<layer>/<name>/`. Каталоги `.claude/`, `.agents/`, `.cursor/`, `.opencode/` в корне — генерируемые зеркала, они в `.gitignore`.
2. `name` во frontmatter == имя каталога. Иначе агент отбрасывает скилл молча.
3. `name` уникален по всему репозиторию, включая другие слои: агент видит плоское пространство имён.
4. Правило живёт ровно в одном скилле. `practice` не содержит языковых правил, `lang` не содержит процесса.
5. Изменение `description` — breaking change: меняет срабатывание у всех и отбирает запросы у соседей.
6. `.claude-plugin/`, `.codex-plugin/`, `.cursor-plugin/` руками не правятся — генерируются из `registry.yaml`.
7. Удаление скилла = удаление каталога. Заглушка «deprecated, используйте X» продолжает конкурировать за запросы.

## Новый скилл

**Шаг 0 — проверить, что скилл нужен.** Заводить, только если `description` можно написать так, что по любому реальному запросу однозначно выбирается он, а не сосед. Если получается похоже на существующий — это `references/` внутри существующего. `go-style` и `python-style` — разные скиллы. `go-style` и `go-testing` — один.

**Шаг 1 — каталог и frontmatter.**

```bash
mkdir -p skills/<layer>/<name>/{references,scripts,evals}
```

```yaml
---
name: <совпадает с каталогом, ^[a-z0-9]+(-[a-z0-9]+)*$>
description: <что делает>. Use this skill whenever <контексты + синонимы>. Do NOT use for <граница>.
---
```

`description`: 300–700 символов, назначение и триггеры в первых 150 (хвост обрезается частью агентов), явная граница обязательна, конкурирующие соседи названы по имени.

**Шаг 2 — тело.** Императив, английский, ≤500 строк, процедура а не справочник. Раскладка материала:

| Материал | Куда |
|---|---|
| Как принимать решение, порядок шагов, формат вывода | `SKILL.md` |
| Точные формулировки правил, таблицы, краевые случаи | `references/` + правило «читай X, когда вопрос про Y» |
| Что вычисляется детерминированно | `scripts/` |
| Файлы, попадающие в результат | `assets/` |

`MUST`/`ALWAYS` — только для форматов вывода и обязательных шагов; остальное с объяснением смысла правила.

**Шаг 3 — реестр.** Запись со всеми полями: `name`, `layer`, `path`, `version: 0.1.0`, `owner` (команда, не человек), `status: experimental`, `triggers`, `boundaries`. Если скилл делегирует соседу — добавить соседу встречную строку в `boundaries`: валидатор проверяет парность.

**Шаг 4 — профиль.** `experimental` идёт только в `profiles.authors`, в рабочие профили — после прогона евалов. Профиль ≤8 скиллов. `everyone` ставится глобально всем — туда только то, что нужно каждому.

**Шаг 5 — евалы.**
- `evals/evals.json` — 5+ кейсов, метод: одно задание с скиллом и без. Обязателен кейс с чистым входом — проверка, что скилл не выдумывает находки.
- `evals/trigger-evals.json` — ~20 запросов, 10/10, негативы только near-miss: общая лексика, другая задача.
- `evals/routing-matrix.json` в корне — строки, где скилл ожидается, и строки, где он не должен перехватывать соседей. Обе стороны обязательны.

**Шаг 6.** `python3 scripts/validate_skills.py --strict` → 0 ошибок, 0 предупреждений.

## Изменение существующего скилла

Тело — обычный PR. `description` — снять снапшот текущей версии как baseline, прогнать **всю** матрицу роутинга, добавить строку в релизные заметки. Прогона собственных trigger-евалов недостаточно: описание влияет на выбор между скиллами.

## Обновление из upstream

Производные файлы пере-выводятся из источника целиком, точечно не патчатся. Обновить дату синка в шапке файла. Проверить, не ссылается ли на изменившееся правило чеклист в `SKILL.md`: расхождение чеклиста и `references/` — самый частый дефект таких скиллов.

## Конфликт роутинга

Симптом: срабатывает не тот скилл или сразу несколько. Порядок: сверить `boundaries` обоих в реестре → добавить встречные разграничивающие фразы в оба `description` → внести спорный запрос в матрицу с ожидаемым набором → прогнать матрицу целиком. Не удалять триггеры у одного из скиллов — это делает его невидимым вместо разграничения.

## Пороги

| Параметр | Значение |
|---|---|
| `description` | 300–700 символов, триггеры в первых 150 |
| `SKILL.md` | ≤500 строк |
| Оглавление в reference | обязательно при >300 строк |
| Профиль | ≤8 скиллов |
| trigger-evals | ~20 запросов, баланс не хуже 10/10 |
| Прогонов на запрос | ≥3 (триггеринг стохастичен) |

## Команды

```bash
python3 scripts/validate_skills.py --strict          # обязательно перед PR
./scripts/install.sh --list                          # скиллы и профили
./scripts/install.sh --profile <name> --dry-run      # план установки
```

Не хватает проверки — добавляй её в валидатор, а не в текст ревью-чеклиста.

## Definition of Done

- [ ] `validate_skills.py --strict` чист
- [ ] Слой соблюдён: практика без языковых правил, язык без процесса
- [ ] Правило не продублировано у соседа
- [ ] Реестр заполнен, границы парные, скилл входит в профиль
- [ ] Матрица роутинга дополнена с обеих сторон
- [ ] Для производного контента указаны источник и дата синка
- [ ] Скрипты исполняемые, без молчаливых сетевых вызовов
