# Skills

Репозиторий agent capabilities команды. Скилл — версионируемая, тестируемая единица поведения агента, а не сохранённый промпт.

- **`AGENTS.md`** — карта репозитория и команды проверок для кодового агента.
- **`registry.yaml`** — состав, владельцы, границы, профили.

## Установка

```bash
./scripts/install.sh --list                      # что есть и в каких профилях
./scripts/install.sh --profile backend-go        # в текущий проект, все агенты
./scripts/install.sh --profile everyone --global # глобально, минимальный набор
./scripts/install.sh --skill go-style -a codex   # точечно
```

Ставится профилями, а не «всё сразу»: описания всех установленных скиллов постоянно висят в контексте, поэтому питонисту Go-скиллы обходятся в токены на каждой сессии. Глобально — только `everyone`, языковое и платформенное — проектно.

Альтернатива без этого репозитория в PATH: `npx skills add <owner>/<repo> --skill go-style`.

## Конвенции

**Один скилл — одна capability.** Если description начинает описывать две разные задачи, это два скилла.

**description отвечает за срабатывание.** Вся информация «когда применять» живёт там, а не в теле. Ориентир — до ~100 слов: описания всех установленных скиллов постоянно находятся в контексте, поэтому цена растёт линейно с размером репозитория. Формулировать настойчиво (модели скорее недо-триггерят, чем перетриггерят), перечислять реальные контексты и синонимы, и обязательно давать явные границы с соседями — одной фразой, а не списком всего, чем скилл не является.

**Progressive disclosure.** SKILL.md — рабочая инструкция (ориентир до 500 строк), детали — в `references/` с оглавлением в начале файла и с явным правилом «читай раздел X, когда вопрос про Y». Контекст экономится уровнями загрузки, а не выкидыванием полезного.

**Детерминированное — в `scripts/`.** Если результат можно вычислить, его не нужно воспроизводить рассуждением. Скрипт обязан честно сообщать, какие проверки не отработали, чтобы отсутствие вывода не читалось как «всё чисто».

**MUST/ALWAYS — только там, где нарушение ломает результат.** В остальных случаях объяснять смысл правила: так модель корректно обрабатывает случаи, которых нет в инструкции.

**Source of truth снаружи — фиксировать явно.** URL источника, дата синка и правило «пере-выводить из upstream, а не патчить на месте» — в шапке каждого производного файла.

## Оценка

Два независимых измерения, не смешивать:

1. **Срабатывание** — `trigger-evals.json`, 20 запросов, примерно поровну should-trigger и should-not-trigger. Ценность в near-miss негативах: запросы, которые делят с скиллом лексику, но требуют другого. Очевидно нерелевантные негативы ничего не измеряют. Прогонять каждый запрос несколько раз (триггеринг стохастичен) и держать train/test split, иначе description переобучится под тестовый набор.
2. **Качество исполнения** — `evals.json`, одно и то же задание с скиллом и без него. Скилл имеет смысл только если стабильно лучше baseline. При обновлении существующего скилла baseline — снапшот предыдущей версии, это защита от регрессий.

Смотреть не только pass rate: время и токены — часть результата. Ассерты, которые проходят и с скиллом, и без него, ничего не различают — их надо переписывать. Для вкусовых скиллов автопроверки не выдумывать: там сравнительная человеческая оценка.

## Ревью

Merge требует чтения диффа, а не только зелёных evals. Скилл — это исполняемые инструкции плюс код в `scripts/`, который поедет на машины всей команды. Проверять:

- [ ] Содержимое не выходит за пределы того, что заявлено в description.
- [ ] `registry.yaml` обновлён, границы с соседними скиллами прописаны с обеих сторон.
- [ ] Есть владелец и оба набора evals.
- [ ] Для производного контента — указан источник и дата синка.
- [ ] Скрипты не тянут неожиданных зависимостей и не делают сетевых вызовов молча.
